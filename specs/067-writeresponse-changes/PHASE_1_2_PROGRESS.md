## Architecture & Design Decisions

### Change Tracking Pipeline

The RxDatasets architecture uses a **Delta-based change tracking system**:

```
Write Operation (Put/Delete/etc)
    ↓
Determine Change Type (NEW/CHANGED/DELETED/NONE)
    ↓
Create Delta Record with (EntityName, ChangeType, CRC32)
    ↓
Apply Delta to Index & Storage
    ↓
Return WriteResponse (internal struct)
```

**Challenge Identified**: The internal `Delta` record contains the detailed change information we need, but it's not exposed to the gRPC service layer where we have access to HTTP headers.

**Available Approaches**:

1. **Static AsyncLocal Storage** (Recommended for Phase 2+ continuation)
   - Store last Delta in thread-local variable after each write
   - Retrieve in WriterServiceImpl when mapping response
   - Minimal code changes

2. **Interface Extension** (Breaking change)
   - Modify IDatasetWriter<T>.WriteResponse to include List<DetailedChange>
   - Requires changes to all implementations and consumers
   - Not recommended for this scope

3. **Wrapper Service Layer** (Recommended for Phase 2+)
   - Create proto-to-domain mapping layer that reconstructs changes
   - More complex but cleanest separation
